# MORISE PLAY LAB Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build an authenticated PLAY surface with three original browser games, server-owned deterministic sessions, validated results, and SYSTEM progression hooks.

**Architecture:** A shared Play Hub selects from a typed game registry. Each run starts a server-owned challenge session, the client submits only an action log, and a server validator computes the result before recording progression. The games remain lightweight DOM/CSS interactions so mobile web performance stays strong.

**Tech Stack:** Next.js 16 App Router, React 19, TypeScript, Vitest, Supabase PostgreSQL/RLS/RPC.

**Spec:** docs/superpowers/specs/2026-09-28-play-lab-design.md

## Global Constraints

- Keep the visible surface to a single PLAY experience selector.
- Experimental games do not alter the canonical 40-game inventory.
- No client-authoritative scores or XP.
- No fake leaderboards or fake player counts.
- No heavyweight 3D dependency in this module.
- Every validated completion must be idempotent.
- Mobile target: 390x844 with no horizontal overflow.

## Review Focus

- Tampered action logs or scores must be rejected by server-side validators; tests belong in game validator tests.
- Replaying a completion request must not grant duplicate progression; test in the result service/RPC integration path.
- Expired or already-completed sessions must not be completable twice; test in play session service tests.
- Rapid input/double-submit must leave one result; test client and server completion path.
- Direct access while signed out must redirect to authentication; test Play route with browser QA and route-level checks.
