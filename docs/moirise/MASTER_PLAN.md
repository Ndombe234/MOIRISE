# MOIRISE — MASTER PLAN CANONIQUE

MOIRISE = réseau social Otaku + création + jeux + découverte + SYSTEM intelligent. La complexité est interne.

## Portes visibles
SYSTEM | PLAYER | SOCIAL | WORLD | PLAY | CREATE

Les capabilities internes (messages, groupes, quiz, jeux 2D/3D, création image/video/audio/music, events, collections, Living Objects, Convergence, etc.) ne créent pas automatiquement des boutons.

## Core loops
AI: Observe → Context → Intent → Policy → Plan → Resources → Execute → Validate → Correct/Ask → Commit → Experience.

AI evolution: Observe limitation → Capability Gap → Hypothesis → Design → Candidate code/algorithm → Sandbox → Tests → Benchmark → Policy/Security → Canary → Promote/Reject → Rollback.

Game: Idea → Intent → GameSpecification → Engine → Content/Assets → Validate → Simulate → Test → Preview → Version → Publish → Runtime.

Community: user-created groups + AI detection/proposal under privacy/consent policy.

## Boundaries
M01 identity/security primitive.
M03 private messaging/social.
M11 community ownership/roles.
M12 real future/event state.
M13 world-change authority.
M14 reward authority.
M15 AI orchestration and AI Lab, not superuser.

External AI providers are auxiliary instruments. Local/zero-API execution is supported where capability/policy permits.

## Rule
A feature is not considered documented from its name alone. It needs owner, trigger, context, inputs, permission, state, persistence, validation, events, UI states, errors, fallback, observability and tests.
