# MOIRISE — DETAIL LEVEL GOVERNANCE

## 1. Permanent rule

When the project owner asks **« détaille »**, every active PLAN.md and every active TECHNICAL_DESIGN.md is expanded to the next detail level.

Level progression:
- D0 = current canonical baseline
- D10 = first tenfold precision increase
- D100 = tenfold precision increase over D10
- D1K = tenfold over D100
- D10K = tenfold over D1K
- and so on.

The factor applies to **engineering precision**, not artificial word inflation.

## 2. Required expansion axes

Every increase must deepen, where relevant:
actor, trigger, preconditions, inputs, exact order, state machine, authority, mutation, persistence, transaction, idempotency, concurrency, projection, cache, events, errors, recovery, privacy, security, provenance, resource limits, performance, observability, browser behavior, mobile behavior, accessibility, tests, rollback and DONE criteria.

AI-enabled capabilities must additionally deepen:
intent, context scope, requirements, capability, tool, task graph, resource reservation, execution target, validation, correction, memory, evidence, benchmark, autonomy and evolution.

## 3. No duplicate authority

A detail expansion may add references and contracts but must not create a second owner for the same rule. Shared mechanisms remain in their canonical owner documents.

## 4. Media rule

Image, photo, video, Reel, Story, audio and music use the same general fabrication discipline as games:
authorize → analyze → abstract → transform/create → validate → provenance → owner commit → publish.

A surface change or lexical obfuscation is not treated as a copyright-safety strategy. The system must favor original expression and meaningful transformation under applicable policy.

## 5. Social rule

Feed, Stories, Reels, photos, reposts, remixes, DMs, groups and profile surfaces must remain inside the six global doors:
SYSTEM, PLAYER, SOCIAL, WORLD, PLAY, CREATE.

## 6. Viral rule

A feature is not considered socially complete merely because it has a share button. Its plan should define immediate user value, a reason for another person to care, a next action, a return path, discovery rules, privacy and anti-spam controls.

## 7. Time rule

Each detail request must be accompanied by a revised project time estimate. The estimate is based on:
- remaining implementation scope;
- integration complexity;
- test burden;
- current repository health;
- automation leverage;
- time actually available from the owner.

Detailing itself does not mechanically multiply implementation time by ten. Better contracts can reduce uncertainty while also revealing additional implementation work.

## 8. Completion definition

MOIRISE is only 100% complete when the relevant feature is:
specified → implemented → persisted securely → tested → integrated → verified in desktop and mobile browser flows → resilient to dependency failure → observable → production-ready.
