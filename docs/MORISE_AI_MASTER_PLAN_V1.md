# MORISE AI — PLAN MAÎTRE UNIQUE V1\n\nDate: 2026-09-29\nStatut: PLAN MAÎTRE DE L’IA\nProjet: Ndombe234/MOIRISE\n\n## 0. Objet\nCe document unifie la conception de MORISE AI : cognition, mémoire, apprentissage, filtrage, création multimodale, création de jeux, observation utilisateur, auto-évaluation, évolution contrôlée, optimisation des ressources et providers externes.\n\nLes 15 modules fonctionnels de MORISE restent la structure du produit. MORISE AI est une couche transversale et évolutive.\n\nPrincipe : PLAYER / ENVIRONMENT → OBSERVATION → FILTER → UNDERSTAND → PLAN → ACT → VALIDATE → RESPONSE → REMEMBER → LEARN → IMPROVE\n\n## 1. MORISE CORE\nContext Engine; Intent Engine; Reasoning Engine; Planning Engine; Decision Engine; Memory Engine; Learning Engine; Skill Engine; Tool Engine; Creative Engine; Evaluation Engine; Resource Engine; Evolution Engine; Version Manager; Rollback Manager; Safety/Policy Engine; Data Filter; Provenance Engine; Provider Router; Scheduler.\n\nLe Core ne dépend d’aucun provider externe. Les providers sont des ressources de soutien, d’acquisition d’expérience, d’accélération ou de fallback.\n\n## 2. OBSERVATION ET CONTEXTE\nLe système construit un Context Pack minimal : session, locale, module, expérience, intention explicite, événements autorisés, préférences non sensibles, état du jeu, signaux du monde, disponibilité des capacités/providers et politique de confidentialité.\n\nPas de profilage psychologique caché, pas de collecte illimitée et pas d’envoi automatique de contenu privé à un provider non autorisé.\n\n## 3. ACTION ET COMMUNICATION\nMORISE peut comprendre, planifier, utiliser des outils, recommander, traduire, créer, analyser et proposer des améliorations. Les messages SYSTEM restent naturels : guidance, découverte, réaction, succès, création, avertissement, erreur.\n\nLe SYSTEM ne prétend jamais avoir effectué une action qui n’a pas réellement réussi.\n\n## 4. DATA FILTER\nUne sortie brute ne devient jamais automatiquement une connaissance.\n\nRAW DATA → PROVENANCE → PRIVACY → SAFETY → QUALITY → ORIGINALITY/COPYRIGHT → DUPLICATION → RELEVANCE → LEARNING ELIGIBILITY → ANALYSIS → CANDIDATE → VERIFICATION → VALIDATED KNOWLEDGE\n\n## 5. APPRENTISSAGE\nMORISE apprend de ses propres expériences, tests, créations, erreurs, retours utilisateurs autorisés, résultats des providers externes, données publiques utilisables et benchmarks locaux.\n\nApprentissage individuel : personnalisation d’un Player sans contamination automatique des autres.\nApprentissage collectif : signaux agrégés et filtrés ; un seul utilisateur ne peut pas modifier une règle globale.\n\n## 6. MEMORY ENGINE\nWorking Memory, Short-Term Memory, Long-Term Memory, Semantic Memory, Experience Memory, Player Memory, World Memory, Creator Memory, Skill Memory et System Observation.\n\nLa RAM sert à exécuter. La mémoire persistante doit rester séparée de la RAM. Supabase/PostgreSQL, stockage objet et recherche sémantique peuvent fournir la persistance ; aucun service de mémoire IA externe n’est obligatoire.\n\n## 7. POSTHOG\nPostHog = observation/expérimentation, pas cerveau. Flux : MORISE EVENT → POSTHOG → AGGREGATION → ANALYSIS → LEARNING CANDIDATE → OFFLINE EVALUATION → SAFETY/POLICY → CANARY → METRICS → APPROVE/ROLLBACK.\n\nPostHog ne modifie jamais directement la production et ne reçoit pas automatiquement les conversations privées ou médias personnels.\n\n## 8. ORIGINAL-FIRST\nTout contenu créatif passe par : INTENT → CREATIVE BRIEF → ORIGINALITY POLICY → PROVIDER/LOCAL MODEL → PROVENANCE/LICENSE → SAFETY/MODERATION → STORAGE → PUBLISH/PRIVATE.\n\nPas de reproduction volontaire de personnages, scènes, logos, marques ou assets d’anime/manga/jeux protégés, ni imitation d’artiste identifiable.\n\n## 9. CREATIVE ENGINE\nCapacités : texte, image, vidéo, musique, audio, TTS, STT, vision, BD/comic, traitement photo, embeddings, recherche et modération.\n\n## 10. GAME CREATOR\nTrois moteurs 2D génériques : Adventure, Battle, Puzzle.\n\nPipeline : PLAYER IDEA → GAME DESIGNER AI → GAME SPEC → ENGINE SELECTION → RULES → CONTENT → ASSETS → VALIDATION → SIMULATION → TESTS → VERSION → PREVIEW → PUBLISH/PRIVATE.\n\nLes jeux sont générés via une Game Specification/DSL/JSON validée, pas via l’exécution directe de code arbitraire.\n\nValidation : schema, règles, états inatteignables, conditions impossibles, ressources, permissions, originalité, sécurité, performance, simulation et régression.\n\nLes expériences 3D restent supportées via des engines/adapters approuvés supplémentaires.\n\n## 11. SELF-CODING ET EVOLUTION\nUne limite détectée produit une candidate d’amélioration.\n\nEXPERIENCE → LIMIT DETECTED → GAP DIAGNOSIS → SOLUTION CANDIDATE → IMPLEMENTATION → SANDBOX → TESTS → SECURITY → BENCHMARK → OLD VS NEW → POLICY GATE → PROMOTE / REJECT → VERSION\n\nAucun code généré ne peut lire les secrets, modifier RLS, écrire directement en production, appeler un provider hors registre ou exécuter des commandes arbitraires.\n\n## 12. RESOURCE ENGINE\nMORISE mesure CPU, GPU, RAM, stockage, concurrence, latence, réseau et disponibilité des modèles.\n\nOptimisations : cache, batching, parallélisation, compression, quantification, offloading, traitement par morceaux, priorités, arrêt précoce et réutilisation de calculs.\n\nObjectif : augmenter le travail utile par unité de ressource, sans prétendre créer physiquement de la RAM ou des unités de calcul.\n\n## 13. MEMORY OPTIMIZATION\nHot data, warm data, cold storage, compression, déduplication, lazy loading, prefetch adaptatif, eviction et checkpoints.\n\n## 14. MULTI-USER SCHEDULER\nLes demandes sont classées : légères, normales, lourdes, background. Les tâches lourdes peuvent être mises en queue. Plusieurs ordinateurs pourront former un Compute Pool plus tard.\n\n## 15. OFFLINE / ONLINE\nOffline : Core, mémoire, skills locales, modèles locaux disponibles, jeux, évaluation et optimisation.\nOnline : recherche, nouveaux providers, nouveaux modèles, synchronisation et nouvelles données.\nL’internet augmente les possibilités mais ne définit pas l’identité du Core.\n\n## 16. PROVIDER REGISTRY\nChaque provider doit avoir : provider_id, capabilities, base URL, auth method, secret env name, models, request schema, response schema, rate limits, pricing/free tier, usage commercial, licence/attribution, privacy/data retention, timeout, retry, health check, fallback priority et enabled state.\n\nAucune feature métier ne doit appeler directement un SDK provider ; elle passe par un adapter.\n\n## 17. PROVIDERS VÉRIFIÉS / CANDIDATS\n\n### Gemini\nSecret attendu : GEMINI_API_KEY.\nGemini API utilise une clé API ; Google AI Studio crée un projet et une clé. Google indique que les nouvelles clés AI Studio sont des clés d’autorisation depuis le 28 mai 2026 et que les anciennes clés standard non migrées sont rejetées en septembre 2026. La clé doit donc être traitée comme un secret serveur et son type doit être validé avant production.\nCapacités candidates : texte, multimodal, vision, image, outils/function calling et autres modèles disponibles dans l’API. Sources actuelles : documentation Gemini API.\n\n### DeepSeek\nSecret attendu : DEEPSEEK_API_KEY.\nOpenAI-compatible : https://api.deepseek.com\nAnthropic-compatible : https://api.deepseek.com/anthropic\nUne seule clé DeepSeek suffit pour les deux formats. Les modèles actuels documentés comprennent deepseek-flash et deepseek-v4-pro. MORISE doit utiliser un seul adapter DeepSeek avec deux transports de protocole.\n\n### Pollinations\nSecret attendu : POLLINATIONS_API_KEY.\nBase actuelle : https://gen.pollinations.ai\nLes générations actuelles nécessitent une clé API ; l’API expose texte, image, vidéo, audio, TTS, STT et embeddings, ainsi que des endpoints compatibles OpenAI. Les clés serveur ne doivent jamais être exposées au frontend.\n\n### Cloudflare Workers AI\nSecrets/variables attendus : CLOUDFLARE_ACCOUNT_ID et CLOUDFLARE_API_TOKEN.\nLa REST API exige un Account ID et un API token avec les permissions Workers AI appropriées. Des endpoints OpenAI-compatible existent pour des modèles texte et embeddings. Cloudflare AI Gateway peut ajouter logging, cache, rate limiting et routage unifié.\n\n### OpenRouter\nSecret attendu : OPENROUTER_API_KEY.\nOpenRouter est traité comme provider agrégateur. L’API exige une clé même si certains modèles ont actuellement un prix de 0 $. La disponibilité des modèles gratuits doit être considérée comme dynamique.\n\n### Puter\nStatut : CANDIDATE — auth, quotas et modèle économique à vérifier avant activation.\n\n### FreeToUse Music API\nURL fournie : https://api.freetouse.com/v3/openapi.json\nStatut : MUSIC LIBRARY CANDIDATE — licence et usage commercial à vérifier avant apprentissage ou publication.\n\n### Autres providers évoqués\nVireonix, Murakumo, Kilo AI, AI Horde, AI Horde OpenAI API, Cehpoint AI, OVH AI Endpoints, Quillly, Openverse, Internet Archive, Hugging Face, Replicate, Firecrawl, LibreTranslate et autres restent en statut CANDIDATE jusqu’à vérification technique et contractuelle.\n\n## 18. SUPABASE SECRETS\nLes valeurs des Secrets Supabase ne sont pas exposées par le connecteur disponible ; MORISE ne doit donc jamais inventer ni copier de secret dans Git.\n\nLes noms connus par conception sont des noms attendus uniquement : GEMINI_API_KEY, DEEPSEEK_API_KEY, POLLINATIONS_API_KEY, OPENROUTER_API_KEY, CLOUDFLARE_ACCOUNT_ID, CLOUDFLARE_API_TOKEN, POSTHOG_API_KEY, etc.\n\nLe projet Supabase MOIRISE est actuellement ACTIVE_HEALTHY. Aucune Edge Function n’était détectée au moment de la vérification ; la passerelle serveur Provider Router devra donc être créée explicitement.\n\n## 19. PROVIDER HEALTH ET FALLBACK\nÉtats : PLANNED → CONFIGURED → AUTHORIZED → ENABLED → EXECUTING → DEGRADED → ERROR → DISABLED/UNAVAILABLE.\n\nOrdre de recherche possible : accès gratuit/anonyme quand le provider l’autorise → API key → autre provider → local → Compute Pool → cache → mode dégradé → UNAVAILABLE.\n\nLe Router choisit selon capacité, confidentialité, qualité, latence, coût, quota et disponibilité.\n\n## 20. CRÉATION ET APPRENTISSAGE À PARTIR DES PROVIDERS\nExemple image : Gemini ou autre provider → résultat → provenance → filtre → analyse → caractéristiques utiles → expérience → connaissance candidate → validation.\n\nExemple musique : bibliothèque autorisée → analyse tempo/structure/énergie/instrumentation → patterns généraux → connaissance musicale candidate. Un fichier musical n’est pas automatiquement autorisé comme donnée d’entraînement : la licence doit autoriser l’usage prévu.\n\nExemple texte : provider → réponse → vérification → erreurs/patterns → stratégie candidate.\n\nLe principe reste : EXTERNAL RESULT → EXPERIENCE → FILTER → ANALYZE → VALIDATE → KNOWLEDGE/SKILL.\n\n## 21. SÉCURITÉ AGENTIQUE\nLes agents modernes peuvent présenter des risques de prompt injection, exécution d’outils et compromission de chaîne d’approvisionnement. Les règles MORISE doivent donc imposer permissions minimales, isolation, intégrité des outils, observabilité, validation et fail-closed sur les opérations sensibles.\n\n## 22. MÉTRIQUES D’ÉVOLUTION\nMORISE n’est pas déclarée plus intelligente parce qu’elle possède plus de code. Les indicateurs d’amélioration sont : meilleure réussite, moins d’erreurs, meilleure planification, meilleure récupération, meilleure qualité créative, meilleur usage mémoire, meilleur rendement calcul et meilleure détection des limites.\n\n## 23. RÈGLE MAÎTRE\nMORISE utilise des IA externes aujourd’hui pour augmenter ses capacités et acquérir des expériences, tout en construisant progressivement ses propres connaissances, compétences, stratégies, optimiseurs et composants locaux afin de réduire sa dépendance demain.\n\nPLAYER DÉCRIT → MORISE CONÇOIT → PROVIDER/LOCAL PRODUIT → MORISE FILTRE → MORISE ANALYSE → PLAYER UTILISE → FEEDBACK → AI LAB → AMÉLIORATION VALIDÉE → MORISE v+1
